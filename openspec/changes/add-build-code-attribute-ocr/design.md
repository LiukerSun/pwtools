## Context

动机见 proposal.md。已发布的 0.9.40 将第三方属性写入 `weapon_build_codes.attributes`，保存时会查询目录，且已有保护同一方案旧快照的故障处理。`BuildCodeAttributes` 当前只有来源、查询时间、参考价和八项主要属性。

C++ `LocalOcr::Recognize` 内部完成检测与文字识别后直接调用 `ParseScoreboard`；Python 引擎已经有 `read_lines` 通用文本及坐标层，但 `/recognize` 同样固定返回战绩结果。用户提供的 M7 面板在现有 Python 引擎中实测读出了枪名、八项属性、价格、容量、开火模式、初速和声音传播距离；这证明文字识别可复用，尚未证明 C++ 专用面板解析及各种截图均可用。

基础改枪码规格尚在已完成的 `add-weapon-build-codes` 变更中。本次不自动归档或同步该变更；新增独立能力描述个人属性扩展。

## Goals / Non-Goals

**Goals:**
- 同一份字段语义在 C++、Python、Rust 和 TypeScript 间保持一致；识别只是候选值，保存依据用户确认。
- 账号身份、方案身份、来源优先级和省略/清空语义明确，避免错绑和兼容性数据丢失。
- 图片与文字仅在内存中处理，识别取消、失败与过期响应不会产生服务端业务记录。

**Non-Goals:**
- 不实现任意改枪码解码、配件反推、属性计算器或跨用户公共上传目录。
- 不从进度条长度估算数值、对缺失字段猜值、识别精校配置或将截图价当作实时价。
- 不持久化图片或完整 OCR 文本，不改变现有战绩识别、截图快捷键归单或账本入账流程。

## Decisions

### 1. 增加独立面板解析，共用推理基础设施

C++ 抽取内部文字行（文本、置信度、坐标）识别层，保留 `Recognize` 的战绩返回格式；新增 `RecognizeBuildAttributes` 和纯函数面板解析器。Python 使用 `read_lines`，新增面板解析器和 `/recognize-build-attributes`，与 `/recognize` 共享同一个 worker、锁和执行器，避免两个入口并行占满 OCR 内存。

按字段标签和同一行右侧数值绑定，而不是全图数字出现顺序；标签允许受控别名和空格归一化，数字处理千位分隔和单位。冲突、重复或低置信候选仅给出待核对提示，无法可靠解析则保持空值。枪名只作为匹配提示；模式和核心码仍来自用户输入，不从枪名或时间推断。

替代方案是直接复用战绩返回值或另装 OCR 模型；前者字段和几何结构不符，后者没有当前样本证据支持新增依赖。

### 2. 使用统一、受控的属性字段

候选值和保存输入采用固定键：`damage`、`armor_damage`、`range_m`、`recoil_control`、`handling`、`stability`、`hip_fire`、`fire_rate_rpm`，附加 `capacity`、`fire_modes`、`muzzle_velocity_mps`、`sound_distance_m` 和 `price`。数值允许空值，保留 0 与缺失的区别；射速、容量和价格为整数，开火模式为全自动/单发/点射的有序去重枚举。单位由字段确定，不接受用户任意单位或任意属性名。

所有数值必须有限、非负；除价格外数值使用 1,000,000 上限作输入保护，不把伤害或操控武断限制为100。价格上限沿用安全整数范围内的项目金额保护值 9,000,000,000,000，但仅表示哈夫币参考价、不参与金额账本。至少一项主要属性有数值才能保存个人快照，只有价格或枪名不能当作有效枪支属性。

展示八项主要属性时沿用既有“肉伤、甲伤、射速、射程、后座、操控、稳定性、腰射”名称；详情展示单位、附加字段和截图参考价。手工来源不显示第三方加成 `change`，不把“初始属性”图例误读成属性值或宣称已获取基础/加成差值。

### 3. 个人快照与服务目录快照分开存储

新增可空 `manual_attributes JSONB` 字段，既有数据库 `attributes` 仍专存第三方快照，不迁移或改写旧值。个人快照包含固定字段、来源 `ocr_confirmed` 或 `manual`、识别发生时间（可空）、服务端确认时间及规范化方案身份：枪名、模式、核心码。

现有 POST/PATCH 输入增加可选 `manual_attributes`：省略代表同一方案保留原快照；对象代表验证并替换；显式 `null` 代表清除个人属性、恢复目录展示。对象的方案身份必须与请求的规范化改枪码一致，客户端不能自行提供确认时间或第三方来源。后端区分省略和 null，不使用会合并两者的普通 `Option<T>` 反序列化。

GET、创建和修改响应增加 `manual_attributes` 与 `provider_attributes`，原 `attributes` 返回有效属性：有个人快照时优先，否则目录快照。有效主要属性沿用兼容结构，附加字段以新增可选字段表达，个人来源的 `provider_id` 为 null；`lookup_status` 保持第三方匹配语义，界面不再用它描述已存在的个人快照。个人快照采用整体优先，不把目录中不同配置的缺失字段自动混入。

第三方查询仍可更新目录快照，不覆盖个人快照；仅保存个人属性时不等待第三方请求，避免上游服务异常拖慢人工保存。无个人输入的原有创建流程仍查询目录。

替代方案是复用唯一 `attributes` 字段；这会把用户值和目录值混为一谈，既难恢复来源，也容易被自动查询覆盖。

### 4. 预览与保存分别授权和执行

新增 `POST /api/weapon-build-codes/recognize-attributes`，账号鉴权后接收现有图片信封（PNG/JPEG/WebP，原图12 MiB、4000万像素、请求18 MiB），在内存验证后转发 Python 专用接口；只返回 `weapon_name`、字段候选、必要置信度/警告和缺失状态，不写表、不调用 OSS。图片路由单独使用大请求限制，普通 CRUD 保持原有小表单限制。

桥接方法 `recognizeBuildCodeAttributes(image)`：Windows 从 WIC 和原生 OCR 读取，验证当前登录会话，直接返回候选，不上传原图；浏览器通过上述鉴权 API 调用服务端 OCR。本机沿用现有识别超时和图片限制；浏览器端识别方法采用可覆盖后端35秒排队与35秒执行的80秒超时，不沿用普通请求15秒超时。服务繁忙、超时、无文字和无面板字段分别提示，均可继续手工录入。

确认后的属性通过现有私人 POST/PATCH 保存，无需识别预览 token，也不将 OCR 来源声称为可信自动认证。Rust 对任何客户端提交的结构都重新校验。

### 5. 校对状态属于当前方案草稿

面板支持选择文件和聚焦导入区域时 Ctrl+V 粘贴；文本输入框中粘贴改枪码或备注保持正常行为。显示截图预览和可编辑字段，缺失/低置信字段突出提示，保留“确认截图与当前改枪码对应”确认项。识别到不同枪名时阻止直接接受，需更正方案枪名或明确确认截图用于当前枪名；保存仍记录用户确认来源，不宣称校验代码内容。

再次识别默认填充空字段，已人工修改字段保留；替换全部需显式选择。更换图片、方案身份、关闭编辑器或退出账号都会使旧识别请求失效，释放预览 URL 并丢弃迟到结果。更改核心码/枪名/模式时提醒并清空个人候选和确认项；保存端同样清除不再属于当前身份的旧快照。仅改备注或完整码文字形式但身份一致时保留快照。

截图预览、候选属性和确认状态都加入已有未保存修改保护、保存单飞和窗口关闭/退出/更新保护。

## Risks / Trade-offs

- [数字和标签错位、光效遮挡] → 使用坐标及标签约束，保留缺失和候选警告；用户确认后保存，不把候选直接发布。
- [错误截图绑定有效改枪码] → 枪名冲突提示、身份绑定与明确确认；无法用 OCR 验证核心码实际配装，来源如实显示个人确认。
- [第三方模式差异或价格波动] → 不混合来源，显示确认/采集时间与“截图参考价”，不当作实时值。
- [共享推理重构影响战绩] → 保留原接口默认行为，跑现有原生 API/OCR 与 Python 战绩回归，并新增专用解析 fixture。
- [旧客户端擦除个人属性] → 三态输入和身份校验，旧客户端同身份 PATCH 省略新字段时保留。
- [用户原图作为私有业务资料] → 不提交用户截图到 Git；测试使用等价合成文本/几何 fixture，原图只在本机用于 opt-in 实测。

## Migration Plan

1. 增加可空字段和输入/响应扩展，默认 null，验证旧客户端、账号隔离及原属性保留；数据库迁移只增字段。
2. 先部署兼容 Rust API 和 Python OCR 专用接口，验证仅预览无表/OSS写入；OCR 与 API 均需更新，不能只部署 API。
3. 再构建桌面客户端，实测本机面板识别、校对保存和重启读取；用户截图作为本机验收资料保留于忽略目录。
4. 回退客户端或 API 时保留可空字段和个人快照，不执行删除数据的逆迁移。旧 API 不会展示个人值，回退窗口暂停相关编辑以免重新绑定后留下错误个人快照；恢复新 API 后再次校验快照身份再展示。

## Open Questions

无阻塞范围的未决项。其他分辨率、裁剪和主题的识别覆盖率需用新增 fixture 与本机实测逐步验证；不预先承诺所有游戏界面均能自动识别。
